# AmneziaWG Selective Route

Клиент AmneziaWG для Home Assistant OS. Через туннель уходит только трафик к адресам, которые попались в DNS-ответах для имён из списка (и их поддоменов), и к указанным IPv4-префиксам. Маршрут по умолчанию LTE не меняется. Свой DNS-сервер дополнение не запускает и настройки DNS Home Assistant, Supervisor и хоста не трогает: остаются DHCP-резолвер роутера и Tailscale MagicDNS.

Образы собираются для `amd64` и `aarch64`. Базовые образы Home Assistant с 2026.03 для `armv7` не публикуются.

## Как это устроено

Дополнение работает в сети хоста и поднимает `awg0` процессом `amneziawg-go`. Рядом `awg` из `amneziawg-tools`. Модуль ядра не нужен.

Конфиг применяется через `awg setconf`, не через `awg-quick`:

- маршрут по умолчанию хоста не подменяется;
- `DNS=` из конфига не меняет резолвер;
- `PreUp`/`PostUp`/`PreDown`/`PostDown` не выполняются;
- `FwMark` отбрасывается, чтобы внешние пакеты туннеля сами в него не завернулись.

`AllowedIPs` внутри туннеля принудительно `0.0.0.0/0`. Это только разрешение шифровать то, что уже попало в интерфейс. Что туда попадёт, решает политика маршрутизации.

```text
DNS-ответ (UDP или TCP, порт источника 53) на любом интерфейсе
  libpcap копирует кадр, сам пакет не задерживается
        |
        v
  qname или CNAME в цепочке — имя из списка или его поддомен?
        |
        да -> A-адрес в nft set routed_v4 на route_timeout (по умолчанию сутки)
              AAAA в строгом режиме -> routed_v6, пакеты туда reject

пакет к адресу из набора или из списка CIDR
  -> mark 0x77 -> rule priority 5100 -> table 51820 -> dev awg0

всё остальное -> основная таблица -> LTE
```

Сниффер только читает копии через `AF_PACKET`. Если `dns-snoop` умер, DNS идёт как раньше. Очередь NFQUEUE не используется: даже с `bypass` зависший слушатель задержал бы каждый DNS-ответ на хосте, включая MagicDNS. NFLOG на этом ядре требует модуль `nfnetlink_log`, которого может не быть, поэтому выбран libpcap: он видит мост hassio, `tailscale0` и остальные интерфейсы через устройство `any` и ничего не задерживает.

Из-за копии, а не удержания ответа, первое соединение к только что увиденному адресу может уйти в LTE раньше, чем адрес попадёт в набор. Следующее уже идёт в туннель. При включённом `warmup` точные имена из списка резолвятся один раз на старте через системный резолвер, без смены DNS, чтобы этот гонка для них была реже. Поддомены так не угадать: они появляются, когда кто-то их реально запрашивает.

Имя `openapi.tuyaeu.com` в списке покрывает и `a.openapi.tuyaeu.com`, и CNAME, который на него указывает. Каждое нужное родительское имя надо указать. Отдельные поддомены перечислять не нужно, если клиент их запрашивает.

Выученные адреса (`ip`, имя, срок) пишутся в `/data/learned.json` вскоре после изменения и при остановке. На старте непросроченные записи сразу возвращаются в nft-набор с оставшимся таймаутом. Новый DNS-ответ заново ставит полный `route_timeout`.

IPv6 в туннель не заворачивается. В строгом режиме увиденные AAAA для подходящих имён отбрасываются. Без строгого режима они идут обычным путём. Если глобального IPv6 на LTE нет, это ни на что не влияет.

Не видно DNS поверх HTTPS и TLS (`dns.google`, DoH в приложениях): в пакете нет открытого ответа. Такие имена в набор не попадут, пока их не узнает обычный UDP/TCP DNS.

Исключения, которые не маркируются:

- `100.64.0.0/10` (Tailscale);
- `192.168.2.0/24` и `exclude_cidrs`;
- сеть Supervisor `172.30.32.0/23`;
- loopback, link-local, multicast;
- IP endpoint.

Правило `priority 5050` отправляет внешний UDP до сервера AmneziaWG в основную таблицу. Правило `5100` только для метки `0x77` и стоит перед типичными правилами Tailscale (~5210). Запросы к системному DNS идут на адрес резолвера, а не на выученный адрес имени, поэтому в строгом режиме до handshake они не попадают в blackhole.

Дополнение пытается поставить на `awg0` loose `rp_filter`. Если `/proc/sys` только для чтения, в логе будет предупреждение. Тогда на хосте:

```bash
sysctl -w net.ipv4.conf.awg0.rp_filter=2
```

Если `net.ipv4.conf.all.rp_filter=1`, ядро берёт максимум и strict-проверка режет ответы. Поставьте и `all`, и `awg0` в 2. Tailscale обычно уже ставит `all=2`.

## Установка

1. Магазин дополнений → Репозитории → `https://github.com/Waitancheg/ha-awg-routing`.
2. Установите **AmneziaWG Selective Route**. Первая сборка на устройстве компилирует `amneziawg-go` в один поток.
3. Вставьте клиентский конфиг в `awg_conf` (в YAML блоком `|`) или заполните ключи, адрес и endpoint. Параметры AmneziaWG 2/3 (I1–I5, S3–S4, HeaderProtectionKey) проходят во вставленном конфиге. Пример без настоящих ключей:

   ```yaml
   address: 10.8.0.2/32
   endpoint: vpn.example.com:51820
   domains:
     - openapi.tuyaeu.com
   cidrs: []
   exclude_cidrs:
     - 192.168.2.0/24
   strict: true
   warmup: true
   ```

   `0.0.0.0/0` в `cidrs` отвергается. Нулевые Jc/Jmin/Jmax в конфиг не пишутся.

4. Запустите. DNS в Home Assistant менять не нужно. В логе будет `watching DNS responses` и, если включён warmup, строки `warmup`.

## Проверка

С хоста HA OS:

```bash
awg show awg0
# запрос, который и так делает HA, или вручную
dig openapi.tuyaeu.com A +short
nft list set inet awg_pbr routed_v4
ip route get <этот-адрес> mark 0x77
ip route show table 51820
```

При свежем handshake в таблице `51820` — `default dev awg0`. Пока handshake старше 180 секунд и строгий режим включён — `blackhole default`. Чужое имя в набор не попадает. `curl -4 https://example.com` остаётся на LTE, если `example.com` не в списке. `tcpdump -ni awg0` показывает пакеты туннеля.

Поддомен: `dig www.openapi.tuyaeu.com` после того, как в списке есть `openapi.tuyaeu.com`, должен добавить адрес в тот же набор.

В Home Assistant:

- `binary_sensor.amneziawg_tunnel` — `on`, если handshake моложе 180 секунд;
- `sensor.amneziawg_last_handshake`, `sensor.amneziawg_rx_bytes`, `sensor.amneziawg_tx_bytes`;
- `sensor.amneziawg_routed_ips` — сколько IPv4 сейчас в динамическом наборе;
- `sensor.amneziawg_snooped` — сколько A/AAAA ответов подошло под список.

Это состояния REST, не отдельная интеграция.

Файл `/data/learned.json` внутри дополнения переживает перезапуск. После старта те же адреса снова в `nft list set inet awg_pbr routed_v4`, пока не истёк их срок.

## Остановка

Штатная остановка сохраняет кэш, затем снимает таблицу `awg_pbr`, правила 5050 и 5100, таблицу 51820 и `awg0`. Если процесс убили без скрипта:

```bash
nft delete table inet awg_pbr
ip rule del priority 5100
ip rule del priority 5050
ip route flush table 51820
ip link del awg0
```

DNS при этом ничего восстанавливать не нужно: его не меняли.

## Права

Нужны сеть хоста и `NET_ADMIN`: метки, NFLOG и интерфейс живут в сетевом пространстве HA OS. AppArmor выключен, потому что стандартный профиль режет netlink nftables и tun. `SYS_MODULE` не нужен. Роль manager не запрашивается: DNS Supervisor не меняется.

## Чего эта сборка не проверяла

На живом Home Assistant OS дополнение не запускалось: нет Supervisor, CoreDNS и Tailscale рядом. Локально собраны `amd64` и `aarch64` (у aarch64 ELF `EM_AARCH64`). На amd64 в сетевом пространстве контейнера проверены `dig` к имени из списка, поддомен/CNAME, чужое имя, blackhole строгого режима, запись кэша и его возврат после перезапуска сниффера, и то, что `dig` отвечает, пока сниффер остановлен. Под qemu nftables netlink для aarch64 не работает, поэтому полный прогон сниффинга там не повторялся. На хосте HA стоит глазами проверить, что ответы CoreDNS и MagicDNS (`100.100.100.100`) видны в наборе и что правила Tailscale на месте.
