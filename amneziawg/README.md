# AmneziaWG Selective Route

Клиент AmneziaWG для Home Assistant OS. Через туннель уходит только трафик к перечисленным доменам и IPv4-префиксам. Всё остальное, включая маршрут по умолчанию LTE-модема, не меняется.

Проверено собирается для `amd64` и `aarch64`. Образы Home Assistant с релиза 2026.03 публикуются только для этих двух архитектур, поэтому `armv7` здесь нет.

## Как это устроено

Дополнение работает в сети хоста (`host_network`) и поднимает интерфейс `awg0` процессом `amneziawg-go`. Рядом лежит `awg` из `amneziawg-tools`. Модуль ядра `amneziawg` не нужен: протокол считается в userspace, достаточно `/dev/net/tun` и `NET_ADMIN`.

Конфиг туннеля применяется через `awg setconf`, а не через `awg-quick`. Из-за этого:

- в основную таблицу маршрутов не попадает маршрут по умолчанию;
- `DNS=` из конфига не переписывает резолвер хоста;
- `PreUp`/`PostUp`/`PreDown`/`PostDown` не выполняются;
- `FwMark` из конфига отбрасывается, чтобы внешние UDP-пакеты туннеля сами не ушли в `awg0`.

`AllowedIPs` внутри туннеля принудительно `0.0.0.0/0`. Это только криптомаршрутизация WireGuard: какой трафик, уже попавший в интерфейс, можно шифровать. Выбор, что туда попадёт, делает политика маршрутизации хоста.

```text
запрос DNS
  Home Assistant -> CoreDNS Supervisor -> dnsmasq на 172.30.32.1:53
                                              |
                                              | A-запись домена из списка
                                              v
                                        nft set routed_v4 (таймаут)

пакет
  daddr в routed_v4 или в списке CIDR
      -> mark 0x77
      -> ip rule priority 5100
      -> table 51820
      -> default dev awg0

всё остальное
      -> основная таблица
      -> маршрут по умолчанию LTE
```

Домены попадают в набор в момент ответа DNS, а не отдельным циклом резолва. dnsmasq добавляет адрес до того, как отдаёт ответ клиенту, так что первое соединение уже видит маршрут. Таймаут элемента — `route_timeout` (по умолчанию сутки). CoreDNS кэширует ответ не дольше часа, поэтому набор живёт дольше кэша и длинное соединение не перескакивает обратно на LTE, пока имя ещё закэшировано. Повторный запрос обновляет таймаут.

AAAA для перечисленных доменов не резолвится в настоящий IPv6-адрес. dnsmasq отвечает `100::1` (discard-префикс RFC 6666), а nftables сразу отклоняет пакеты в `100::/64`. Остальной IPv6, включая адреса Tailscale, не трогается.

Исключения, которые никогда не маркируются:

- `100.64.0.0/10` (Tailscale);
- `192.168.2.0/24` и всё, что перечислено в `exclude_cidrs`;
- сеть Supervisor `172.30.32.0/23` и подсеть моста `hassio`, если она другая;
- loopback, link-local, multicast;
- IP endpoint и IP вышестоящих DNS.

Правило `priority 5050` дополнительно отправляет внешний UDP до самого сервера AmneziaWG в основную таблицу. Правило `priority 5100` стоит перед типичными правилами Tailscale (около 5210) и совпадает только с меткой `0x77`, поэтому `tailscale0` и `100.64.0.0/10` остаются у Tailscale. Дополнение пытается включить на `awg0` loose `rp_filter`: ответ приходит из туннеля, а обратный маршрут к этому источнику в основной таблице — это LTE. Если `/proc/sys` в контейнере только для чтения, в логе будет предупреждение. Тогда на хосте:

```bash
sysctl -w net.ipv4.conf.awg0.rp_filter=2
```

Если `net.ipv4.conf.all.rp_filter` равен 1, ядро берёт максимум и strict-проверка всё равно выбрасывает ответы. В этом случае поставьте и `all`, и `awg0` в 2. Tailscale обычно уже делает `all=2`.

## Почему DNS устроен именно так

Home Assistant Core не читает `/etc/resolv.conf` хоста. Его резолвер — CoreDNS плагина Supervisor (`172.30.32.3`). Список вышестоящих серверов задаётся `ha dns options` и API `POST /dns/options`.

Валидатор Supervisor принимает только `dns://<IPv4>` без порта. `dns://172.30.32.1:5354` и `dns://172.30.32.1#5354` отклоняются. Поэтому dnsmasq слушает порт 53 на адресе шлюза сети hassio, обычно `172.30.32.1`. Из контейнера CoreDNS этот адрес доступен, а `127.0.0.1` хоста — нет: это loopback самого контейнера CoreDNS.

`manage_dns` (по умолчанию включён) при старте делает `POST /dns/options` с `dns://172.30.32.1` и `fallback: false`, а при остановке возвращает прежние значения. Для этого у дополнения роль `manager`. Если API недоступен, в логе будет та же команда, её можно выполнить из SSH:

```bash
ha dns options --servers dns://172.30.32.1 --fallback=false
ha dns info
```

Адрес берите из лога: строка `dns <адрес>:53`. Если мост называется иначе и адрес не `172.30.32.1`, в логе будет фактический IP.

Оговорки CoreDNS, от них зависит, насколько строгий режим действительно строгий:

- В `forward` CoreDNS после серверов из `ha dns options` всегда остаются DNS хоста (поле `locals`, обычно резолвер LTE). Политика `sequential`: пока наш dnsmasq отвечает, до них очередь не доходит. Если дополнение лежит и health-check CoreDNS помечает его мёртвым, новые имена резолвятся мимо nftables и в набор не попадают.
- `fallback: true` при NXDOMAIN, SERVFAIL и REFUSED спрашивает Cloudflare в обход dnsmasq. Дополнение выключает fallback. Иначе ответ может обойти набор.
- Имена `*.local.hass.io` CoreDNS отдаёт сам и в наш форвардер не отправляет. mDNS не затрагивается.
- Пока дополнение не запущено, а DNS уже указывает на него, резолв прочего трафика стоит. `boot: auto` и watchdog поднимают процесс обратно. Watchdog смотрит, что живы `amneziawg-go` и dnsmasq, а не то, что handshake свежий: мёртвый удалённый сервер не должен перезапускать контейнер по кругу.
- Вышестоящий DNS ходит обычным маршрутом, не через туннель. Так имена резолвятся и когда туннель ещё не поднялся. Если имя отдаёт правильный адрес только из сети сервера (split-horizon), этот адрес с LTE не узнать. Для Tuya и AWS eu-central-1 проблема в TCP-таймауте, а не в DNS, поэтому резолв через LTE здесь уместен.
- Общий адрес CDN, однажды попавший в набор, будет уходить в туннель до таймаута, даже если им пользуется другой сайт.

## Установка

1. В Home Assistant: Настройки → Дополнения → Магазин дополнений → меню справа сверху → Репозитории. Добавьте:

   `https://github.com/Waitancheg/ha-awg-routing`

2. Обновите магазин и установите **AmneziaWG Selective Route**. Первая установка собирает образ на самом устройстве: качаются исходники AmneziaWG и Go-модули, сборка `amneziawg-go` идёт в один поток, чтобы не упереться в память. На слабой плате это несколько минут.

3. Заполните конфигурацию. Либо вставьте клиентский конфиг в `awg_conf` (в редакторе YAML, блоком `|`), либо оставьте его пустым и заполните ключи, адрес, endpoint и параметры Jc/Jmin/Jmax/S1/S2/H1–H4. Для AmneziaWG 2.x/3.x (I1–I5, S3–S4, HeaderProtectionKey, padding) вставляйте конфиг целиком: эти поля проходят как есть.

   Пример структурированных значений, без настоящих ключей:

   ```yaml
   address: 10.8.0.2/32
   endpoint: vpn.example.com:51820
   domains:
     - openapi.tuyaeu.com
   cidrs: []
   exclude_cidrs:
     - 192.168.2.0/24
   strict: true
   ```

   `0.0.0.0/0` в `cidrs` дополнение отвергает. Jc/Jmin/Jmax равные 0 не записываются в конфиг: подставьте значения с сервера, если обфускация включена.

4. Запустите дополнение. В логе должны появиться адрес DNS, endpoint и фраза про strict mode.

5. Проверьте, что Supervisor смотрит на наш резолвер:

   ```bash
   ha dns info
   ```

   В `servers` должен быть `dns://172.30.32.1` (или адрес из лога), `fallback` — `false`. Если `manage_dns` выключен, выполните команду из лога.

## Проверка

Команды ниже — с хоста Home Assistant OS (SSH на порт 22222 или терминал с доступом к хосту). `dig` есть в дополнении; с хоста его может не быть, тогда поставьте запросы из контейнера дополнения или используйте `nslookup`.

Туннель жив, handshake не нулевой:

```bash
awg show awg0
```

Имя резолвится, AAAA — discard-адрес, адрес попал в набор:

```bash
dig @172.30.32.1 openapi.tuyaeu.com A +short
dig @172.30.32.1 openapi.tuyaeu.com AAAA +short
dig @172.30.32.1 www.openapi.tuyaeu.com A +short
nft list set inet awg_pbr routed_v4
```

Поддомен попадает в тот же набор. Чужое имя — нет:

```bash
dig @172.30.32.1 example.com A +short
```

Маршрут с меткой смотрит в таблицу туннеля, без метки — в обычный default:

```bash
ip route get "$(dig @172.30.32.1 +short A openapi.tuyaeu.com | head -n 1)" mark 0x77
ip route show table 51820
ip route get 1.1.1.1
ip rule show
```

У свежего handshake в таблице `51820` будет `default dev awg0`. Пока handshake старше 180 секунд и включён строгий режим, там `blackhole default`.

Счётчик nft растёт на запросе к домену из списка и не растёт на постороннем:

```bash
nft list chain inet awg_pbr tag
curl -4 -v --max-time 20 https://openapi.tuyaeu.com
curl -4 -v --max-time 20 https://example.com
nft list chain inet awg_pbr tag
```

Пакеты в туннеле:

```bash
tcpdump -ni awg0 -c 20
```

Чужой сайт, который показывает внешний IP (`curl -4 https://ifconfig.me`), должен показать адрес LTE. Сайт из списка, если он показывает IP, — адрес сервера AmneziaWG.

Tailscale и LAN на месте:

```bash
ip rule show
ip route show table 52
ping -c 1 192.168.2.1
```

Правила Tailscale (приоритеты около 5210–5270) дополнение не удаляет. `ip route get … mark 0x77` насильно ставит метку; настоящий пакет в LAN её не получает, потому что `192.168.2.0/24` в наборе исключений.

Строгий режим: остановите сервер или подставьте неверный endpoint. `ip route show table 51820` покажет blackhole, `curl` к домену из списка не уйдёт в LTE, `curl https://example.com` продолжит работать.

В Home Assistant после старта ядра появляются:

- `binary_sensor.amneziawg_tunnel` — `on`, если handshake моложе 180 секунд;
- `sensor.amneziawg_last_handshake`;
- `sensor.amneziawg_rx_bytes` и `sensor.amneziawg_tx_bytes`;
- `sensor.amneziawg_routed_ips` — сколько IPv4 сейчас в динамическом наборе (CIDR из конфигурации в это число не входят).

Сущности пишутся через `POST /core/api/states` и не регистрируются интеграцией, поэтому у них нет устройства в реестре. Они видны в состояниях и пригодны для автоматизаций.

## Остановка

Штатная остановка снимает таблицу nftables `awg_pbr`, правила приоритетов 5050 и 5100, таблицу маршрутов 51820 и интерфейс `awg0`, и возвращает прежний DNS Supervisor. Если контейнер убили без скрипта остановки, с хоста:

```bash
nft delete table inet awg_pbr
ip rule del priority 5100
ip rule del priority 5050
ip route flush table 51820
ip link del awg0
```

DNS, если он так и указывает на дополнение:

```bash
ha dns info
ha dns options --servers dns://1.1.1.1 --fallback=true
```

Или восстановите серверы, которые были до установки. Копия на момент переключения лежит в `/data/dns-backup.json` внутри дополнения, пока остановка не прошла успешно.

## Права

Дополнению нужны сеть хоста и `NET_ADMIN`: метки, правила и интерфейс живут в сетевом пространстве HA OS. AppArmor выключен: стандартный профиль режет netlink nftables и создание tun, а профиль «разрешить всё сетевое администрирование» ничего не добавляет к уже выданному `NET_ADMIN`. Роль `manager` нужна только чтобы менять DNS Supervisor. `SYS_MODULE` не запрашивается.

## Чего эта сборка не проверяла

На живом Home Assistant OS дополнение не запускалось: нет устройства с Supervisor, CoreDNS и Tailscale. Локально собраны образы `amd64` и `aarch64` (у aarch64 бинарник ELF `EM_AARCH64`, dnsmasq с `nftset`). На amd64 в отдельном сетевом пространстве контейнера проверены разбор конфига, наполнение nftset из DNS, blackhole строгого режима, HTTP health и очистка правил. На хосте HA отдельно стоит глазами проверить `ha dns info`, что CoreDNS действительно ходит на `172.30.32.1:53`, и что правила Tailscale не сдвинулись.
